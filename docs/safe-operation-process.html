Codex-only constrained workflow

How the RB Safe-Operation Process Works

A plain-language guide to the optional constrained route, its static verification boundary, and the assurances it does and does not provide.

Purpose Route choice Verification modes Process Bounded patch Authority Recovery Meaning of safe Verification Assurance limits Examples

1. Purpose

The constrained route reduces the chance that an agent silently widens an approved operation, acts against stale repository state, overlooks declared side effects, or loses the execution record. It binds one current phase to an exact plan, policy, repository snapshot, capability profile, evidence set, approvals, and audit trail.

Static-only first release. The current route can read files, apply an already specified patch, or ask a bounded model to return an exact proposed text diff. The model does not apply the diff. It cannot run tests, builds, linters, type checkers, applications, browsers, benchmarks, shell commands, or network-dependent validation.

2. Choose the standard route or the constrained route

Standard route

Use for ordinary software behaviour, scientific code, refactors, migrations, integrations, and any task whose correctness depends on running code.

The standard route uses automated behavioural tests, appropriate integration or contract coverage, CI-equivalent checks, and review+fix.

Constrained route

Use only for narrow operations on exact files whose acceptance can be proved from resulting file state.

It provides tighter scope, immutable handoffs, deterministic capability checks, semantic safety assessment, and durable audit records.

Runtime-dependent acceptance criteria are rejected. A phase that needs pytest, application startup, browser interaction, performance measurement, or external observation must return to the standard route.

3. Machine-typed verification modes

Every constrained success criterion and verifier check uses a closed form:

<mode>::<description>
ModeMeaningFirst-release status
static_file_stateProvable by inspecting the resulting repository file state.Supported
executable_testRequires running a test, build, linter, type checker, benchmark, or command.Rejected
runtime_observationRequires starting or interacting with the software.Rejected
external_observationRequires observing a deployment, remote service, or other system outside repository state.Rejected

Untyped strings are invalid. The deterministic preflight checks the mode before the semantic assessor runs.

static_file_state::README.md contains the canonical command
static_file_state::product_diff contains only the declared paths
static_file_state::undeclared_effects are absent

The following examples cannot enter the first-release constrained route:

executable_test::pytest tests/test_parser.py passes
runtime_observation::the service answers /health
external_observation::the deployed endpoint reports healthy

4. Process flow

1. Route selection. The user explicitly chooses constrained; the agent never infers it.
↓
2. Optional project policy. The user may use rb-create-safe-operation-policy to turn ordinary-language path restrictions into a typed preview and confirmed fixed-root policy. Canonical absence preserves baseline behaviour.
↓
3. Phase selection. rb-execute-plan selects one current phase for linear delivery. rb-sprint may select one current phase after an adaptive review checkpoint. Either workflow must confirm that all acceptance is static before constrained compilation.
↓
4. Compilation. rb-create-low-level-plan binds schema-3 operations, paths, effects, evidence, stop conditions, later-phase continuity, fixed source and effective policy identities, provider and resource grants, and typed verification requirements. A bounded operation authorises a proposal, not a direct write.
↓
5. Plan preflight. The runtime validates identities, policy, adapter capabilities, provider and resource grants, evidence, effects, approvals, and every verification mode. Unsupported or untyped criteria produce immutable safe: false.
↓
6. Plan assessment. The coordinator builds the complete typed request and a fresh no-tool assessor checks the operation envelope for hidden scope, ambiguity, prompt injection, detrimental effects, recovery realism, and dishonest classification of behavioural claims as static. The user does not copy hashes or construct a semantic response file.
↓
7. Proposal and exact-patch assessment. For bounded work, a model returns a strict diff. The coordinator materialises it without writing, checks it deterministically, and asks a different no-tool assessor to judge those exact proposed bytes.
↓
8. Coordinator commit. Only an unchanged accepted proposal may run. The coordinator records an apply intent and approval receipts, rechecks the fixed policy before implicit parent creation and every read or mutation, then applies the prepared bytes and records each target. The model never crosses this write boundary.
↓
9. Static verification and handoff. The earlier plan-assessment packet binds selected sources by hash and metadata but does not contain their text. Immediately before a later proposer call, the coordinator re-reads those files, checks the same bindings, and places their exact complete text in the fixed proposer packet. allowed_read_tools governs only additional interactive proposer discovery, while read_roots must cover the selected source files deliberately supplied by the coordinator. After application, the coordinator captures policy-permitted contents only for snapshot-selected files and declared expected product paths, then builds a complete typed verifier packet. This verification is separate: a create-only Codex proposal does not need to add its new product targets as read roots merely so their postimages can be verified. Denied state is recorded as unobserved, not unchanged. A context-separated no-tool verifier reports semantic coverage, evidence, effects, and findings against the exact packet. The trusted transport attaches the immutable request and post-execution identities from that packet, so the model is not asked to copy hashes. The coordinator validates the complete response, records state and limitations, and stops before compiling another phase.

5. Optional fixed project policy

The fixed file <project-root>/.rb-safe-operation-policy.json lets a user add repository-owned restrictions without writing JSON. It is optional and can only narrow the installed global policy. The runtime never searches a parent directory or accepts a different action-bearing path.

User states a restriction in ordinary language
                 ↓
No-tool translator returns a typed proposal
                 ↓
Python computes the complete effective-authority difference
                 ↓
Human confirms that exact preview
                 ↓
Coordinator reacquires the shared lease and rechecks source identity
                 ↓
Python atomically writes only the fixed policy and durable records
                 ↓
All later constrained artifacts bind the new policy identity

An exact or subtree rule can independently deny read, create, modify, or delete. “Write” expands to all three mutation capabilities. A denied read is pruned before content hashing, instruction loading, role transmission, or descendant enumeration. The preview also explains that restrictions are prospective: they cannot erase information already present in a conversation, provider log, Git history, backup, copy, cache, or process memory.

policy-preview computes the complete restriction change. Relaxing a restriction requires a separate explicit confirmation. The apply step recomputes the preview rather than trusting the supplied classification, uses compare-and-swap against the exact old source hash, and records an indeterminate outcome if replacement occurred but durable completion could not be proved.

6. How a bounded model change is actually applied

The model communicates its intended code or text change as a standard unified diff inside a strict typed AgentPatchProposal. It does not write a script for later execution and does not receive a filesystem write tool. The runtime treats the diff as untrusted data.

Coordinator builds exact source context
                 ↓
Proposer model returns a strict unified diff
                 ↓
Python parses the diff and materialises candidate files in memory
                 ↓
Deterministic checks derive paths, actions, hashes, metadata and effects
                 ↓
Fresh no-tool assessor judges the exact preimages and postimages
                 ↓
Coordinator records an apply intent and consumes exact approvals
                 ↓
Python writes the already assessed bytes and records each committed target
                 ↓
Fresh verifier checks the committed static file state

What the proposer decides

The proposer can choose the exact wording or code within the approved goal, file roots, patch actions, effects, and permitted adaptations. It returns the complete diff, claimed file inventory, claimed effect IDs, and bounded evidence.

What Python decides

The coordinator independently derives which files would be created, modified, or deleted. It computes exact preimages and candidate postimages, checks metadata and paths, applies policy and approvals, controls state transitions, and performs the write.

What the patch assessor decides

A different fresh context judges whether the exact proposed content fits the plan and whether it introduces hidden, detrimental, security, privacy, audit, or verification effects. It receives no product tools.

The coordinator supplies complete material source content rather than presenting hashes as if they were semantic evidence. If the required content cannot fit the approved data or resource limits, the run stops before mutation.

7. Provider, tool, and resource authority

A schema-3 bounded plan names the fixed project-policy identity, an explicit provider grant, and a finite run-resource grant. The provider grant fixes the adapter, endpoint, model and revision, credential audience, permitted source-data class, retention and training disclosures, response types, expiry, and provider ceilings. The resource grant separately limits proposer calls, assessor calls, model requests, mediated reads, bytes, patch size, tokens, elapsed time, and cost. It also says whether malformed unified-diff syntax may be corrected automatically and how many such attempts are allowed.

The reviewed profile uses the Codex CLI already authenticated through the local Codex application. It does not read an OpenAI API key. Before every role call, the runtime checks the exact executable, CLI revision, model, and ChatGPT login. The call runs ephemerally in a fresh temporary directory with isolated SQLite and log state, a read-only sandbox, strict structured output, and a closed disabled-capability list. The coordinator accepts reasoning lifecycle events and exactly one final typed message; a tool event, unsupported event, malformed stream, missing usage, or inconsistent result fails closed. These controls narrow the available interface, but they do not prove operating-system isolation or expose complete internal service traces. The assurance label therefore remains instruction_only_proposal_host.

The authenticated Codex service receives the deliberately selected source packet and the absolute path names used for policy and file-identity binding. Both must fit the confirmed data classification and account policy. The temporary role directory prevents ambient project discovery; it does not keep the supplied request data on the local machine.

codex-run is the reviewed live path. It remains disabled unless the operator supplies an unchanged confirmed preparation and the explicit --enable-codex-cli switch. In one Python process it performs plan assessment, optional diff proposal, optional patch assessment, coordinator-owned application, and static verification. codex-resume continues the same journalled run after reloading complete call usage. The older framework-run and framework-resume commands are separately selected PydanticAI/OpenAI compatibility paths; they are never an implicit fallback.

The preparation is one authority envelope for all permitted model calls in that unchanged run. The user confirms it once, not once per role call or permitted format correction. Any different run, provider, model, plan, policy, target set, effect set, permission set, expiry, or budget needs a new preview and confirmation.

After a trial, acceptance-summary produces a small typed measurement record containing only role order, assurance profiles, provider and grant identities, calls, tools, tokens, bytes, elapsed time, cost, terminal state, and static-only limits. It deliberately excludes prompts, diffs, source contents, model responses, reasoning, and credential values.

8. Approval timing, crashes, repair, and recovery

One-use mutation approval is not spent when the model is merely asked for a proposal. The coordinator first persists an apply intent that binds the exact accepted patch, assessment, approvals, ordered targets, and every preimage and postimage hash. It then creates matching approval-consumption records immediately before mutation.

Multi-file changes are committed in order and are not described as globally atomic. Nested file creation may create only missing parent components below the approved working directory. Each component is checked against symlinks and conflicting files, created with fixed mode 0755, and fsynced. Removable undeclared extended attributes are stripped. Because macOS automatically adds com.apple.provenance and may refuse to remove it, the coordinator accepts that one attribute only when its value exactly matches the parent; it does not call the resulting metadata empty. Empty components are removed if preparation fails before a file is committed. After each target reaches its postimage, the coordinator checkpoints the committed prefix. On reload it accepts only four understandable situations:

  • all targets are still at their exact preimages, so commit may start;
  • a recorded prefix is at its exact postimages and the rest are exact preimages, so the same accepted patch may continue forward;
  • all targets are at their exact postimages, so the operation is recognised rather than repeated;
  • anything else is unknown state and enters non-resumable human_required.

A correctness repair creates a new immutable repair attempt and a new proposal cycle bound to the verification finding. Eligible repair attempts can remain logically unbounded, while the active aggregate resource grant stays finite. Exhaustion pauses before mutation. A new grant must explicitly replenish the previous one and does not erase earlier usage or permit broader work.

A narrower automatic retry may be confirmed for proposal_format_error. This means the model returned a complete, fully accounted typed response, but its unified diff was malformed. The coordinator keeps the rejected response, writes a typed retry record, confirms that product and protected control state are unchanged, and sends a correction request with a fresh token inside the same unchanged operation. The attempt limit may be unbounded, but the total calls, tokens, bytes, elapsed time, and cost are still finite.

Automatic correction does not cover a forbidden path, wider target set, unsupported action or metadata, safety finding, changed state, unexpected side effect, provider identity change, incomplete call, or uncertain commit. Those conditions still stop, pause, or require a person according to their existing rule.

Every semantic role request is written as a create-only typed record before the provider call. A validated response and its usage record are also written create-only before the lifecycle checkpoint advances. A recovered complete call is added back into the host's aggregate call, token, byte, time, and cost totals before another role can run. Restarting a process therefore does not reset the budget. If the process stops while a call may have happened but no complete response is durable, recovery does not call the provider again. It enters human_required. If the owned host proves it rejected the request before dispatch because the finite grant was exhausted, the run may use paused_resource and an exact replenishment grant instead. This distinction prevents hidden duplicate calls without turning every pre-dispatch budget limit into a terminal failure.

A patch-safety failure is different from an ordinary correctness repair. It enters human_required with the rejected proposal and typed findings. A person can revise and reassess, leave the constrained route, or abandon the run, but cannot relabel that same unsafe proposal as safe.

Runtime installation rollback is separate from run recovery. Setup retains every selected runtime manifest by a content hash. An operator may explicitly select an older retained manifest only while its exact source checkout, launcher, bootstrap interpreter, installed environment, package, and dependency locks remain available and unchanged. The rollback command validates all of those identities before atomically changing current.json. Missing or corrupted rollback material leaves the current installation selected. It does not delete project run records, so audit and recovery state survives installation rollback.

9. What safe: true means

There are two deliberately separate safety verdicts. Plan safe: true means that one exact low-level plan envelope passed deterministic identity, policy, capability, provider, resource, approval, evidence, effect, and verification-mode checks, plus a fresh semantic assessment. Patch safe: true means one exact diff passed its deterministic proposal preflight and fresh semantic patch assessment.

The plan verdict authorises an attempt to obtain a proposal. The patch verdict permits only the coordinator to attempt the exact accepted bytes. Neither is a general claim that the agent, computer, task, code, or resulting system is safe. Relevant drift invalidates the handoff.

10. What verified means

In this first release, verified means the declared static_file_state requirements are covered by coordinator-observed repository state and context-separated verifier evidence, with no blocking or undeclared material effect.

Static verification must never be described as proof that code compiles, tests pass, the application works, performance is acceptable, or integrations behave correctly. Those claims require the standard route.

11. Assurance limits

  • The workflow is semi-formal, not an operating-system sandbox.
  • The Codex roles receive complete bounded packets and no project write interface. Unnecessary Codex capabilities are disabled and observed tool events fail closed, but these process controls do not control unrelated processes or prove operating-system isolation.
  • The Codex and caller-mediated JSON-line boundaries retain instruction-level assurance. Surrounding state checks detect lasting unauthorised mutation after a call; they cannot prove no transient external action occurred.
  • Fresh-context assurance is recorded from the selected adapter and host rather than assumed.
  • Complete child-agent traces are unavailable.
  • The manual approval channel records exact declared consent but does not authenticate a human principal.
  • Hashes bind reviewed artifacts and state; they do not create authorization or tamper-proof storage by themselves.
  • Semantic plan, patch, and verification roles can still miss harmful meaning. Deterministic boundaries reduce the available scope but do not make model judgement infallible.
