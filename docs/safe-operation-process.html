How the RB Safe-Operation Process Works

A plain-language guide to the optional constrained route, its static verification boundary, and the assurances it does and does not provide.

Purpose Route choice Verification modes Process Meaning of safe Verification Assurance limits Examples

1. Purpose

The constrained route reduces the chance that an agent silently widens an approved operation, acts against stale repository state, overlooks declared side effects, or loses the execution record. It binds one current phase to an exact plan, policy, repository snapshot, capability profile, evidence set, approvals, and audit trail.

Static-only first release. The current route can read files, apply approved patches, and use bounded semantic editing limited to read and patch. It cannot run tests, builds, linters, type checkers, applications, browsers, benchmarks, or network-dependent validation.

2. Choose the standard route or the constrained route

Standard route

Use for ordinary software behaviour, scientific code, refactors, migrations, integrations, and any task whose correctness depends on running code.

The standard route uses automated behavioural tests, appropriate integration or contract coverage, CI-equivalent checks, and review+fix.

Constrained route

Use only for narrow operations on exact files whose acceptance can be proved from resulting file state.

It provides tighter scope, immutable handoffs, deterministic capability checks, semantic safety assessment, and durable audit records.

Runtime-dependent acceptance criteria are rejected. A phase that needs pytest, application startup, browser interaction, performance measurement, or external observation must return to the standard route.

3. Machine-typed verification modes

Every constrained success criterion and verifier check uses a closed form:

<mode>::<description>
ModeMeaningFirst-release status
static_file_stateProvable by inspecting the resulting repository file state.Supported
executable_testRequires running a test, build, linter, type checker, benchmark, or command.Rejected
runtime_observationRequires starting or interacting with the software.Rejected
external_observationRequires observing a deployment, remote service, or other system outside repository state.Rejected

Untyped strings are invalid. The deterministic preflight checks the mode before the semantic assessor runs.

static_file_state::README.md contains the canonical command
static_file_state::product_diff contains only the declared paths
static_file_state::undeclared_effects are absent

The following examples cannot enter the first-release constrained route:

executable_test::pytest tests/test_parser.py passes
runtime_observation::the service answers /health
external_observation::the deployed endpoint reports healthy

4. Process flow

1. Route selection. The user explicitly chooses constrained; the agent never infers it.
↓
2. Phase selection. rb-execute-plan selects one current phase and confirms all acceptance is static.
↓
3. Compilation. rb-create-low-level-plan binds exact operations, paths, effects, evidence, stop conditions, later-phase continuity, and typed verification requirements.
↓
4. Deterministic preflight. The runtime validates identities, policy, capabilities, evidence, effects, approvals, and every verification mode. Unsupported or untyped criteria produce immutable safe: false.
↓
5. Semantic assessment. A fresh assessor checks hidden scope, ambiguity, prompt injection, detrimental effects, recovery realism, and dishonest classification of behavioural claims as static.
↓
6. Execution. Only the unchanged safe: true bundle may run. Every identity and repository snapshot is revalidated before mutation.
↓
7. Static verification. The coordinator captures product state and a context-separated verifier reports against the exact typed criteria. Repairs remain inside the approved read/patch envelope.
↓
8. Handoff. The run records hashes, lifecycle state, event head, evidence, limitations, remaining phases, and the exact next action. It stops before compiling another phase.

5. What safe: true means

safe: true means that one exact low-level plan passed deterministic identity, policy, capability, approval, evidence, effect, and verification-mode checks, plus a fresh semantic assessment.

It authorises an attempt to execute that unchanged plan. It is not a general claim that the agent, computer, task, code, or resulting system is safe. Any relevant drift invalidates the handoff.

6. What verified means

In this first release, verified means the declared static_file_state requirements are covered by coordinator-observed repository state and context-separated verifier evidence, with no blocking or undeclared material effect.

Static verification must never be described as proof that code compiles, tests pass, the application works, performance is acceptable, or integrations behave correctly. Those claims require the standard route.

7. Assurance limits

  • The workflow is semi-formal, not an operating-system sandbox.
  • Assessor and verifier read-only behaviour is instruction-only on the current host.
  • Fresh-context separation is requested and recorded but is not host-proven independence.
  • Complete child-agent traces are unavailable.
  • Repository-state comparison can detect lasting changes but cannot prove that no transient external action occurred.
  • The manual approval channel records exact declared consent but does not authenticate a human principal.
  • Hashes bind reviewed artifacts and state; they do not create authorization or tamper-proof storage by themselves.
