# RB Safe Operation

Execute only an unchanged approved schema-3 bundle. A bounded language-model role may propose exact diff bytes, but it never applies them. The deterministic coordinator validates and assesses the proposal, records an apply intent, and alone writes the accepted bytes. Every observation and mutation is rechecked against the fixed project-policy identity. This remains a static-only, semi-formal control workflow rather than an operating-system sandbox.

## Executable Verification Limit

- The first-release global policy does not permit `exec_argv`, `check`, subprocesses, command-capable bounded tools, or delegation. Therefore this workflow cannot run unit tests, integration tests, builds, linters, formatters, type checkers, benchmarks, application commands, or CI-equivalent workflows.
- Every accepted success criterion and verifier check must be typed `static_file_state::<description>`.
- Reject any criterion or check that is untyped or uses `executable_test`, `runtime_observation`, or `external_observation`; deterministic preflight must fail before mutation.
- Do not use source inspection, hashes, generated plans, or agent-reported reasoning as a substitute for executable behavioural evidence.
- If any success criterion depends on executing code or observing runtime behaviour, stop before mutation as unsupported, or enter `human_required` if the limitation is discovered later. Return to the standard route or wait for a reviewed release with contained command capability.
- Reach `verified` only for criteria that are fully and truthfully observable through the supported static file-state operations. A documentation, configuration, schema, or exact text transformation may qualify; ordinary behavioural code changes generally do not.

## Runtime And Preflight

1. Invoke the installed `scripts/run_runtime.py` only through the manifest-recorded absolute bootstrap interpreter using `-I -S -B`, as specified in `references/runtime-contract.md`. It selects only the canonical manifest-pinned environment and ignores legacy environment redirection. If setup is needed, stop and ask the human to run `scripts/setup_runtime.py` with an approved wheelhouse. Normal operation never installs. Setup retains a content-addressed manifest for each installed source. If an installation rollback is needed, stop normal execution and require explicit `scripts/rollback_runtime.py --control-root <absolute-control-root> --manifest-hash <retained-hash>` invocation through the retained bootstrap interpreter with `-I -S -B`. Rollback must revalidate the retained source, launcher, environment, package, locks, and manifest before atomically selecting it; it must not delete project run records.
2. Consume only the fixed create-only `.rb-safe-operation/artifacts/<run-id>/low-level-plan.json` and `assessment-bundle.json` handoffs, plus the exact provider grant, active run-resource grant, adapter capability profile, and required approvals. Revalidate runtime/schema/source/lock identities, plan/assessment/policy/snapshot/grant hashes, approvals, applicable instructions, and current repository state. Schema-1 plans and paused runs are audit-readable only; they must be recompiled and reassessed rather than executed or resumed.
   Before acquiring the lease, invoke manifest-pinned `doctor` for the exact selected profile, fixed project-policy status, supplied grants, four installed schema mirrors, and `static_file_state` modes. Stop on `not_ready` or a profile mismatch. Doctor output cannot replace the plan assessment, grant checks, approvals, snapshot revalidation, or mutation-boundary policy checks, and this skill must not let doctor repair or widen anything.
   For the reviewed Codex-native profile, use manifest-pinned `codex-run` with the fixed low-level plan, unchanged confirmed run-preparation preview, verifier context ID, and explicit `--enable-codex-cli`. This one owned Python process invokes separate ephemeral Codex CLI roles and preserves aggregate usage across them. Use `codex-resume` only for the same journalled run and confirmed authority; it re-adopts every persisted complete role-call record before another dispatch. Never select an ambient executable or model, resolve a different login, reset usage, substitute an API key, or fall back to another adapter. The older `framework-run` and `framework-resume` commands remain separately configured compatibility paths. The `assess`, `coordinate`, and `coordinate-resume` commands remain caller-mediated JSON-line compatibility drivers.
3. Acquire the one project mutation lease at `.rb-safe-operation/execution.lease`. Any existing live, stale, or indeterminate lease stops. The first release has no automatic stale-lease recovery API; a human must investigate and resolve the external control state outside this skill before a newly identified run can be assessed.
4. Reject any stale, changed, unsupported, false, expired, consumed, or insufficiently observed input. Never silently downgrade assurance or leave the approved envelope.
5. Re-run deterministic verification-mode enforcement. Confirm that every success criterion and verifier check is `static_file_state` and observable through an exact coordinator action or coordinator-captured file state. The plan-assessment packet binds selected sources by hash and metadata without their text; immediately before proposal, the coordinator re-reads them, verifies those bindings, and supplies their exact complete text in the fixed proposer packet. `allowed_read_tools` governs only additional interactive proposer reads. Every deliberately selected source file supplied in a bounded proposal packet must be inside that operation's `read_roots` and covered by a repository-read effect. New product targets do not need to be read roots merely for the coordinator to observe their declared postimages during separated verification. Any executable or external requirement is an unsupported-operation stop.

## Execute Exact Operations

1. Let the coordinator perform an approved `read_file` directly. For an exact `apply_patch`, use the shared pure preparation, journalled commit, per-target checkpoint, and recovery implementation described below.
2. Immediately before mutation, repeat lease, plan, policy, capability, approval, instruction, complete snapshot, path, link/inode/device, preimage, metadata, and protected-control checks.
   - For a declared nested create whose parent is absent, let coordinator code create only the missing parent components beneath the bound working directory at fixed mode `0755`. Reject symlink or non-directory components, fsync each new directory, and roll back newly created empty parents if preparation fails before a file commit. Remove removable undeclared extended attributes. On macOS, accept only an exact parent-matching `com.apple.provenance` value when the operating system refuses its removal; do not describe the created metadata set as empty. Do not use an unassessed setup command to create product directories.
3. Record and fsync an `ApplyIntent` before consuming approvals or changing a product file. Consume the exact one-use approvals idempotently after the intent is durable and immediately before commit.
4. Derive the authoritative `ExecutionReport` from observed postimages and effects. No agent or external host may report an exact operation as successfully executed.

## Execute Bounded Proposal Operations

1. Construct a fresh `ProposalContext` for one operation and attempt. It must bind the plan, plan assessment, operation, policy, base snapshot, applicable instructions, complete coordinator-supplied source bundle, runtime-mediated read observations, provider and resource grants, repair attempt where applicable, request token, toolset, and prompt packet.
2. Validate the reviewed Codex executable, version, and ChatGPT login before the workflow can persist its first semantic-call intent. Persist each coordinator-built typed request before its role call, then revalidate the same identity immediately before dispatch. Start the exact pinned Codex CLI ephemerally in a fresh temporary directory with a read-only sandbox, isolated local state, a role-specific strict output schema, and unnecessary Codex capabilities disabled. Supply the complete source bundle in the request. Reject any tool or unsupported event. The role returns typed JSON containing an exact unified diff and claims; it receives no project write interface and cannot use an interactive read tool.
3. Surround every host call with product and protected-control state capture. The Codex process restrictions narrow the interface, but they do not prove operating-system isolation or a complete child trace. An observed unexpected host mutation causes `human_required` and is not described as prevented. Keep the assurance label `instruction_only_proposal_host` for this release.
4. Strictly validate `AgentPatchProposal`, independently parse its standard unified diff, and build a coordinator-owned `BoundedPatchProposal`. Derive path actions, exact preimages and candidate postimages, hashes, byte counts, and metadata fingerprints. Treat claimed paths, effects, evidence, and intent as consistency assertions rather than authority.
   - If, and only if, the confirmed run-resource grant names `proposal_format_error`, the coordinator may automatically ask the proposer to correct malformed unified-diff syntax. Each retry uses a fresh request token inside the same unchanged run, operation, plan, policy, provider, and grant envelope. Persist the rejected typed response, complete role-call usage, and a typed retry record before dispatching again.
   - Enforce the confirmed retry attempt limit. The value may be a non-negative integer or `unbounded`, but every call still consumes the finite aggregate call, token, byte, elapsed-time, and cost ceilings in the same run-resource grant.
   - Never treat a path escape, scope expansion, unsupported action or metadata, stale state, safety finding, incomplete or uncertain provider call, provider-identity change, plan or policy change, unexpected side effect, or ambiguous commit state as a format retry. Those conditions follow their existing fail-closed, pause, or human-intervention path.
5. Prepare the complete UTF-8 patch in memory without writing product or temporary files. Reject binary, mode, symlink, hard-link, rename, copy, traversal, duplicate-target, malformed, over-budget, unsupported-metadata, and out-of-envelope changes.
6. Run deterministic `PatchProposalPreflight` against the exact proposal. Revalidate every material source observation, including non-target reads. A deterministic failure persists typed findings and enters `human_required` without invoking commit.
7. Start a fresh no-tool patch-assessor context. Supply the exact operation, instructions, policy facts, complete material source context, diff, preimages, candidate postimages, effects, and preflight. The assessor judges plan fidelity, hidden scope, prompt injection, detrimental direct and indirect effects, security and privacy changes, and verification interference. It cannot assess its own patch in the proposer context.
8. Let the coordinator validate and sanitise the assessor result and create `PatchAssessment`. Only an exact binding with `safe: true`, complete coverage, and no blocking finding may proceed. This exact patch assessment is separate from the earlier plan-envelope assessment.
9. Revalidate the full authority and state again. Record and fsync the exact proposal-bound `ApplyIntent`, then consume any proposal-bound one-use approvals. Apply only the prepared postimages through coordinator code. Do not generate or execute Python or shell code from the proposal.
10. Checkpoint every committed target, fsync supported file and directory boundaries, preserve supported metadata, remove or report staging residue, and build the authoritative bounded `ExecutionReport` from observed postimages. Continue into separated verification only after all operations are durably complete.
11. Stop for concurrent user change, new path/tool/permission/objective/effect, material uncertainty, audit corruption, stale or conflicting approval, executable acceptance criteria, false static labelling, unknown commit state, or any change requiring reassessment. Never overwrite unexpected user work.

## Repair And Pause

- Reversible local repair may use `attempt_limit: "unbounded"` inside the unchanged envelope. Every repair starts a newly identified proposal cycle bound to the immutable `RepairAttempt` and current verification finding. It must pass the same proposal, preparation, preflight, patch assessment, journalled commit, report, and verification path as the initial attempt.
- Keep finite per-attempt limits and charge proposer calls, assessor calls, model requests, read-tool calls and bytes, request and response bytes, patch bytes, elapsed time, tokens, and provider cost where the adapter can observe them. A failed provider call with incomplete usage stops that host rather than allowing an unaccounted retry. Automatic format correction is allowed only when the unchanged confirmed run-resource grant explicitly enables it and the preceding call has complete usage evidence.
- The active run-resource grant is finite even when semantic repair attempts are unbounded. Exhaustion becomes `paused_resource` before mutation. Resume requires a newly identified grant whose predecessor is the current grant, a non-decreasing issue time, explicit authorization evidence, a new host using that grant, and full state revalidation. Replenishment does not reset history or permit a wider operation.
- At repeated findings, record the attempted hypothesis, observed result, reconsidered assumption, and materially different next strategy. Do not add a fixed repeated-text stop rule.
- Destructive, external, costly, privacy-sensitive, security-sensitive, or irreversible replay requires fresh idempotency proof and remaining one-use approval or a new exact approval.
- Resume only after validating the canonical coordinator bundle, complete event chain, resource-grant chain, persisted proposal cycle, apply journal, reacquiring the lease, and revalidating runtime, policy, plan, assessment, approvals, capability, provider identity, instructions, all source observations, paths, metadata, snapshot, and verification modes. Never re-invoke the proposer when a complete valid proposal already exists. A known pre/post target prefix may recover forward under the same accepted proposal; any unknown state enters non-resumable `human_required`.

## Separated Verification

1. After operations stop normally, capture coordinator-observed product state and enter `verifying`.
2. Request a fresh verifier context without proposer or patch-assessor reasoning. Let the coordinator build and durably record the complete `VerificationRoleRequest`; do not ask a caller to copy tokens, snapshots, hashes, reports, criteria, or effects into JSON. In the reviewed Codex profile, ask the model only for the semantic decision, then let the trusted transport attach the request token and immutable plan, assessment, post-execution snapshot, proposal-cycle, context, and policy bindings from that validated request. Record the actual freshness and no-tool assurance rather than assuming instruction-only or host-enforced behaviour.
3. Compare actual static file state, the exact typed `static_file_state` criteria, verifier checks, expected effects, forbidden effects, evidence gaps, and audit/provenance conflicts against the approved bundle.
4. Require the verifier proposal to return the exact typed requirement strings from the plan. Reject invented, omitted, duplicated, or differently typed criteria and checks.
5. Reject any criterion whose truth depends on running code, tests, builds, linting, typing, benchmarks, application workflows, or external services. Do not infer runtime behaviour from source text.
6. A repairable in-envelope finding may enter `repairing`; then use a separate repair executor and run fresh verification again.
7. Reach `verified` only when the coordinator-observed product snapshot and separated agent-reported verifier evidence cover every typed statically observable criterion, with no blocking or undeclared material effect. Keep `independent_context: false` unless a future host can attest isolation.

## Records And Handoff

- Preserve the canonical plan, policy, plan assessment, provider and resource-grant chain, host capabilities, create-only semantic request and response records, role-call usage, automatic-retry records, proposal contexts, runtime-mediated read records, agent proposals, bounded proposals, deterministic preflights, patch assessments, apply intents, approval-consumption records, coordinator reports, snapshots, manifest, event chain, repair attempts and outcomes, verification artifacts, and typed `HumanIntervention` record for every `human_required` stop. Never repeat a provider call whose durable request has an incomplete or uncertain outcome. A post-stop human decision does not relabel or resume the rejected proposal in place; revision uses a new run and full reassessment.
- For an authorised acceptance trial, run manifest-pinned `acceptance-summary` after the terminal handoff. Record only its typed identities and operational totals. Do not copy prompts, diffs, source contents, model responses, reasoning, or credential values into the acceptance report.
- Redact typed secrets before persistence and omit uncertain free text with a reason. Never change `.gitignore`, stage, commit, delete, or call local hashes tamper-proof automatically.
- End in `verified`, `rejected`, `human_required`, `failed`, or `abandoned`; stop before compiling the next phase.
- Emit a stdout handoff containing state, event head, current phase, all remaining phase IDs, artifact locations, exact next action, enforcement limitations, verification modes, executable-testing limitations, and any human decision required. After the terminal product snapshot, update the canonical external `${CODEX_HOME:-$HOME/.codex}/diary/` continuity record from that handoff; it is control-plane state, not a product mutation. Do not create or change a project-local progress file unless it was an assessed product operation.
